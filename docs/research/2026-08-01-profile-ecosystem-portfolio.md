# Profile ecosystem portfolio: public evidence

**Research date:** 2026-08-01
**Decision investigated:** How can Factory Pilot reach 100+ composable,
production-relevant Profile _recipes_ through permission-aware reuse of public
ecosystems, without manually rebuilding full vertical applications or allowing
external code, services, or data models to become Graph authority?

This memo is a public-source landscape and intake plan, not an adoption,
source-copy, dependency, Candidate, Golden-asset, or provider decision. It
uses only fixed public repository references, release/tag pages, licence files,
and official documentation. The Application Graph remains the source of truth:
only a Factory Draft may be changed, only a Published Revision compiles, and a
Candidate is invisible to the Graph and compiler. See the
[platform boundary](../architecture/application-graph-platform.md) and the
[accepted External Intake design](../superpowers/specs/2026-07-31-external-capability-intake-design.md).

## Reading the evidence

The 43 references below cover 14 domains: restaurant/POS, commerce, CRM,
appointments, ticketing, learning, healthcare administration, inventory and
warehousing, fleet/logistics, HR, property, accounting, support/knowledge/CMS,
and cross-cutting platform services. The fixed ref is a public tag or immutable
SHA as recorded in the machine-readable
[`2026-07-30 portfolio`](../../ecosystem/portfolio/2026-07-30-external-business-logic.json).
It is a reproducible research locator, **not** an approval to fetch, package,
or execute upstream bytes.

Classifications are exclusive:

| Classification                     | Meaning here                                                                                                                                           |
| ---------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------ |
| **Direct dependency**              | A small library could later be pinned behind a Factory-owned boundary; it is not installed or approved.                                                |
| **Provider**                       | An optional external service may later sit behind a Factory contract and a local fixture provider.                                                     |
| **Bounded source reuse candidate** | Permissive-looking material that still needs a separate snapshot, licence decision, exact path-and-line copy ledger, and independently authored tests. |
| **Pattern-only**                   | Read public architecture or vocabulary and independently write Factory code. No source, package, UI, data, or runtime reuse.                           |
| **Excluded**                       | Current licence, attribution, topology, data, or risk policy blocks copying, packaging, embedding, or running it.                                      |

**Observed fact:** a tag/SHA and a primary licence link are public evidence of
a particular upstream snapshot. A release/tag or maintained repository record
is a maintenance signal only; it is not a security assessment or suitability
finding.
**Inference:** the proposed capability names and boundaries are Factory-owned
composition hypotheses. They are not claims that an upstream component can be
reused unchanged.

### Portfolio checks

**Observed facts:** the candidate map contains **43 fixed references** across
the stated 14 domains: 1 direct-dependency, 7 provider, 11 bounded-source,
8 pattern-only, and 16 excluded entries. The existing machine-readable
portfolio contains **108 numbered scenario demand mappings**. The approved
intake design explicitly says that both counts are metadata, not Graph assets
or Candidate promotion authority.

**Inference and product decision:** The limiting factor is not finding another
full application; it is proving a small set of permission-aware, independently
compilable capability contracts. Build recipes from those contracts and use the
portfolio only to test coverage and boundary quality. This should affect
roadmap sequencing: composition kernel and native contracts first; reviewed
direct dependencies/providers second; vertical breadth last.

## Automated bulk intake versus autonomous review-only gates

The accepted design permits automation to remove clerical burden but forbids it
from making adoption decisions. The separation is intentionally strict.

| Automated, quarantine-only bulk lane                                                                                                                                                        | Autonomous review-only gate (cannot be automated into approval)                                                                                  |
| ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------ |
| Validate allow-listed public URL plus exact tag/SHA; resolve tag to commit; archive/tree hash; capture origin, licence, and notice paths.                                                   | Confirm licence compatibility, notices/trademarks/data restrictions, and whether the use is permitted.                                           |
| Generate SBOM from manifests without installation; run pinned offline licence/secret/SAST/dependency scans; create AST/module inventory.                                                    | Review scanner findings, module suitability, the reason a package is insufficient, and a smallest practical boundary.                            |
| Persist immutable acquisition/evidence records in `ecosystem/intake/**`; emit a non-executable `factory.candidate-capability/v1` manifest, fixture, adapter skeleton, and conformance plan. | Review exact copy paths/line ranges, Factory interface, parameter/effect constraints, tests, removal path, and notices destination.              |
| Run Factory-owned, network-denied Candidate conformance; render a read-only promotion packet; report opaque IDs, counts, statuses, and digests.                                             | A named reviewer decides whether to reject or promote through a reviewed commit that independently authors a Golden package or provider adapter. |

Automation must fail one source closed on an unresolved ref, missing or
ambiguous licence/notice, excluded licence, scanner/parser failure, dynamic
execution, secret, unsafe archive, unsupported binary/generated source,
oversized copy proposal, or any Candidate-to-Graph/compiler linkage. It may
never install a dependency, execute downloaded source, create an account,
contact a vendor, accept a licence, waive a finding, copy a fragment into
`packages/`, change a Draft/Published Revision, create a Golden lock, or start
a provider runtime.

## Production-readiness boundary

**Profile count is not production-ready count.** A recipe demonstrates a
plausible, typed composition and a portfolio demand signal. It is not a
deployable product until it has all of the following for its actual bindings:

1. Factory-owned domain, policy, flow, page/experience, and integration
   semantics validated from a Draft and compiled only from a Published Revision.
2. Deterministic compiler output plus focused unit, semantic, role/permission,
   failure, conflict, audit, and generated-runtime evidence.
3. An explicit data classification/retention model and relevant security,
   money, privacy, regulatory, device, or operational review.
4. For any ecosystem use: exact source/package/provider evidence, notices,
   source-copy ledger where applicable, no credential persistence, conformance
   fixtures, retry/idempotency/error mapping, and removal/replacement proof.
5. A reviewed release decision; a `conformance-passed` Candidate alone is
   still quarantined and cannot be selected, locked, published, or compiled.

## Conclusion

**Observed evidence:** permissive libraries, replaceable providers, and
pattern-only/excluded applications span the portfolio, but every full vertical
application brings a runtime, data model, licence, operational, or regulatory
boundary that Factory should not inherit.
**Factory inference:** speed comes from widening a small, governed capability
kernel and composing it into recipes, while the External Intake lane turns
public ecosystem knowledge into auditable, non-executable evidence. The next
product decision is therefore to sequence native capability-contract evidence
and recipe validation—not to approve any source, dependency, provider, or
Candidate described here.
