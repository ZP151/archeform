# Reliable generation and Training Funding design

Date: 2026-09-17
Owner: delivery controller
Authority: founder continuation of the accepted product-scale roadmap and active
long Goal; technology proposals require recorded standing acceptance before
implementation. This design does not supersede technology or threat authorities.

## Product outcome

An ordinary user asks for a training funding approval app. The platform selects
a reviewed definition and assembles the existing Approval family. The user can
create a course request with session date, positive fee and justification, submit
it, understand a returned decision, correct it without rebuilding, resubmit and
read the retained final decision. A long generated application identifier must
not prevent this otherwise supported product from becoming usable.

This delivery adds one distinct job, not a numeric catalogue milestone. Existing
Restaurant, Expense, Purchase, Tasks and Publication behavior remains unchanged.
Historical generated bundles remain immutable. Amended ADR-0068 permits only
six explicit physical-name mappings in future regeneration of the protected
five fixtures; strict inverse comparison must recover their original complete
bundle digests, with every other byte unchanged. The baseline was captured
at `bbb1e23c68f05e3ae213ceaf167737eb0fe86779` before implementation in
`packages/compiler/test/fixtures/five-definition-baseline.json` (SHA-256
`421447a597e6593045b1fe317ed0c83e6469f5540c6156620d05af2503670ae5`).

## Delivery boundaries

1. Repair database naming under ADR-0068. Prove the reproduced long identifier,
   colliding prefixes, schema validity and actual SQL agreement. Preserve Graph
   keys, API identifiers and existing immutable artifacts. Capture the baseline
   before code; never regenerate it to conceal a difference.
2. Implement one shared numeric-domain primitive under ADR-0069 after its own
   independent standing review. Bounds and integrality must survive the whole
   requirement/Blueprint/Graph/compiler path and be enforced by the server. No
   Training or Equipment conditionals and no default positivity for legacy money.
3. Admit Training only after supported definition data, generated UI and an actual
   persisted business journey pass. Required numeric failures include zero,
   negative, nonfinite/malformed direct input and rejected updates without
   receipts/audit/state mutation. Valid correction and exact retry remain usable.

No payment, reimbursement transfer, budget accounting, course enrollment,
calculated totals, date intervals, entitlement, hosted identity or deployment is
claimed. A session date identifies the requested session; no scheduling capacity
or inferred date-order policy is introduced. Equipment remains pending calculated
totals. Real-model selection and ordinary-user effort remain separately unproven.

## Presentation and reuse

Reuse the approved Approval workspace, cobalt tokens, icon buttons, form fields,
record identity, decision history and meaningful detail presentation. Follow the
registry/recipe/template/source-study search order before any shared UI extension.
Do not add a decorative category field to fit the old Publication test harness.
The key phone screen presents course identity, state and the next valid action;
fee and session date are easy to find, with the justification in readable details.
Two materially different courses must remain distinguishable after reload and
in decision history. Familiar refresh actions stay icon-only and accessible;
consequential decisions retain clear labels. No new visual asset is required.

## Acceptance cases and measures

| Dimension            | Required evidence                                                                                                                                                                                                             |
| -------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Assembly reliability | Original failing long identifier compiles, validates and starts in an isolated local runtime; mapped schema and migration agree.                                                                                              |
| Numeric correctness  | Focused boundary/integrality tests; strict malformed-input rejection; actual API create/edit rejection with unchanged persisted state, version, receipts and audit.                                                           |
| Business closure     | Create two distinct requests; submit, return, revise fee/justification, resubmit, approve; retained identities, decisions and data after reload/restart.                                                                      |
| Access and recovery  | Wrong-role/state denial, stale update conflict, interrupted mutation/retry and no duplicate decision or audit. Demo roles are not production identity.                                                                        |
| UI quality           | Actual generated primary/form/outcome images at 390/768/1440; CSS/icon geometry, usable validation, meaningful summaries, reachable actions, no accidental overflow. Inspect images against the approved shared direction.    |
| Compatibility        | Original fixtures unchanged; only the six physical mappings accepted by amended ADR-0068 may differ in future database output, with the strict inverse recovering all five old bundle digests; numeric absence adds no delta. |
| Delivery             | Exact source/compilation/runtime identity, safe evidence, owned-resource teardown, independent review, normal branch push and local/remote equality.                                                                          |

For authored-fixture acceptance, predeclare a prepared-local target of five
minutes from accepted request to usable app, zero technical handoffs and zero
manual rescue within a passing attempt. Report all failed attempts separately.
Do not interpret a prepared-machine sample as an SLA or ordinary-user result.
Record definition count, runtime families, accepted jobs, shared capability edits
and per-product source edits separately. Training should require definition data
and case configuration; platform capability work belongs to the shared count.

Use focused TDD and one independent review for the ordinary naming correction.
Use the existing full contract gate once for the numeric schema/runtime boundary;
include Training acceptance in that same review evidence where practical. This
design adds no extra audit or founder approval layer.
