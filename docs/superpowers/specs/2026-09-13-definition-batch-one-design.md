# First representative definition admission batch

The user authorizes executing the accepted scale roadmap and gradually adding
definitions. The existing consumer flow and approved Approval presentation are
the design baseline. No new visual direction or routine founder confirmation
is needed for this already requested implementation.

## Outcome and chosen approach

Evaluate the six roadmap candidate briefs, then admit only a genuinely distinct
job that the existing family can execute. Publication Review is the first target:
an author drafts content, an editor returns it with a reason, the author corrects
and resubmits the same record, and an editor approves it with retained history.
An auditor reads the decisions. Approval records a review decision; it never
claims to publish to an external channel.

Use one new reviewed data entry with the existing Approval family and generic
projection. Preserve the original four data entries and their exact generated
outputs. This exercises configuration-only expansion from four to five without
introducing a product-specific projector, runtime handler, form or stylesheet.

The alternatives were to admit all six labels immediately, which would count
unsupported behavior, or build new rule engines before any admission, which
would delay useful reuse. The chosen small batch provides one actual product
journey and measured capability gaps for the next shared improvement.

## Product definition

- Definition key: `publication-review`; version `1.0.0`.
- Family: `approval` / `approval-correction/v1`; parameter policy `none/v1`.
- Primary entity: `submission`; actors `author`, `editor`, `auditor`.
- Business fields: `articleTitle` required text; `contentBody` required long
  text; `channel` required enum (`blog`, `newsletter`, `social`, `documentation`);
  `editorialNotes` optional long text. The fixed family owns its status field.
- Keep the existing requester/reviewer/auditor grants, four workflow states,
  seven-page composition, six locks, correction, history and retry semantics.
- Use the existing cobalt Approval shell, native typed controls, library icons,
  status hierarchy and responsive navigation. Relevant content and readable
  summaries matter; decorative photos are not required for a review tool.
- Explicit material exclusions: external publishing, scheduled publication,
  rich-text/media/file storage, multiple review stages, real identity and
  private ownership. An unsupported demand remains a clarification, never an
  inferred consent to this narrower workflow.

## Honest batch classification

Publication Review is the prospective data-only admission. Training Funding
Approval needs an amount-domain constraint: current currency parsing checks a
finite number but permits negative fees, and the Blueprint has no minimum/range
field. A basic cost rule must not be omitted to count this as a finished product.
Travel needs date ordering and declared budget rules; Leave needs interval,
overlap and allowance invariants; Access needs identity/provisioning delivery.
Equipment quantity/cost demands must remain present: an exact Purchase Request
rename is a duplicate control, while quantities or calculated totals require
their own supported rules. No unsuccessful candidate raises the product count.

## Acceptance

New data and generated selection schema must actually be consumed by the public
interpreter adapter. Provider-free authored selections prove parsing,
projection, material-question retention and fallback behavior; they do not
measure real-model classification or ordinary-user success.

Run the actual local consumer-to-immutable-Compilation/verification/Preview
journey and generated PostgreSQL/API/browser workflow. Verify required and
enum inputs, correction/resubmission on the same identity, retained results,
role denial, stale updates and interrupted-action recovery. Inspect actual
primary/input/outcome screenshots at 390/768/1440, including loaded styles,
icons, no document overflow and reachable controls. Use one reusable test case
interface and existing Approval acceptance helpers, not a copied test per app.

Preserve original fixture bytes and compare the original four entries by their
recorded keys; current catalogue growth must not replace historic expectations.
Record registered definitions, actual journey passes, runtime families and
product maturity separately. Local demo roles and viewport tests remain local
evidence. Root owns service lifecycle, source identity, cleanup and Git delivery.
