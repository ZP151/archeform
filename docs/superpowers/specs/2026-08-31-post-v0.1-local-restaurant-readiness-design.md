# Post-v0.1 Local Restaurant Readiness Design

## Status and decision

This design is the selected local-first follow-up to `factory-pilot-v0.1.0`.
The founder requested execution of the previously recommended
`Post-v0.1 Local Onboarding & Supported Acceptance` iteration on 2026-08-31
and explicitly accepted ADR-0024 on 2026-09-01. This document narrows that
accepted direction into an executable product gate.

The selected approach is an additive local operability profile around the
already accepted Restaurant V3 product. It preserves the current Golden
runtime, Graph, lifecycle, compiler, generated runtime, and Compose topology.
It does not reopen product semantics merely to make a new harness pass.

Implementation remains limited to the task state and exact paths authorized by
the PM ledger. ADR-0024 acceptance does not authorize a task before PM advances
that task to `implementing`.

## Outcome

A technical evaluator using a clean checkout on supported Node 22 can follow
one documented path from repository preflight to a running Archeform product:

1. verify the local toolchain without exposing credential values;
2. install the frozen pnpm dependency graph;
3. start an isolated local Archeform stack;
4. open Apps and choose either `Describe a product` or the curated Restaurant
   template;
5. reach the editable Restaurant customer and merchant surfaces;
6. edit at least one Page, Data, Experience, or Access value;
7. Publish an immutable revision, Compile it, and run verification;
8. start the generated preview;
9. place one customer order and complete its merchant fulfilment path; and
10. stop the preview and leave zero run-owned containers, networks, volumes,
    or preview directories.

The deterministic curated-template path is the repeatable local acceptance
authority. The existing guarded real-model Describe path remains a separate
environment-only release gate and never falls back to fixture mode.

## Target cohort and product boundary

The immediate cohort is one to five invited technical evaluators or design
partners who can use a terminal but do not need to understand Application
Graph, package, database, policy-engine, or Docker internals. The product gate
begins at a clean checkout and ends after verified cleanup.

This iteration is local-only. It excludes hosted or multi-user operation,
production identity or tenant isolation, cloud deployment, domains, fleet
operations, production observability, production payments, workflow editing,
new Graph or capability families, new providers, new dependencies, and any
Compose topology change.

## Considered approaches

### A. Additive local operability and real template acceptance — selected

Keep the accepted product and platform contracts, add a safe doctor, a pinned
Node selector, deterministic CI, and a dedicated full-stack template journey.
This closes the nearest user-facing gap without creating a second platform.

### B. Move directly to hosted Private Beta — rejected for this iteration

This would require identity, tenant, deployment, secret-management,
observability, support, and rollback decisions. It crosses several unaccepted
security and technology boundaries before local onboarding is repeatable.

### C. Continue Graph, capability, or provider expansion — rejected

The shipped Restaurant product already proves the governed generation path.
Additional breadth would increase architecture surface while leaving the first
supported user journey difficult to reproduce.

## Architecture

### Supported toolchain contract

- The repository continues to support Node `>=22.11.0 <23` and pnpm 9.
- The accepted selector is `.node-version` containing exactly `22.11.0`, the
  minimum supported runtime.
- CI verifies both `22.11.0` and the current Node `22.x` line.
- `packageManager` remains `pnpm@9.0.0`; the lockfile stays byte-identical
  unless a separately approved dependency change is required.
- No new package is needed for version parsing, process execution, or tests.

### Doctor contract

`node scripts/doctor.mjs` is a read-only, cross-platform preflight. It has two
explicit scopes:

- `toolchain`: Node range, pnpm major and declared package-manager version,
  Git availability, and repository-root detection;
- `local`: every toolchain check plus Docker client/server, Docker Compose,
  `.env` presence, and required environment variable names.

The doctor prints only check names, safe versions, and missing variable names.
It never prints environment values, `.env` lines, command environments,
credentials, raw prompts, or raw provider responses. It returns zero only when
every check in the selected scope passes and returns a non-zero code with
bounded remediation text otherwise.

### CI contract

GitHub CI is deterministic and credential-free. It has `contents: read`
permission, uses official actions pinned to full commit SHAs, enables
`pnpm@9.0.0` through Corepack, installs with `--frozen-lockfile`, runs the
toolchain doctor, generates the Prisma client with a non-routable placeholder,
then runs formatting, typecheck, tests, build, third-party notice verification,
and source-study verification.

CI does not start Docker, call a model provider, publish artifacts, deploy,
write repository contents, or claim product acceptance. The local isolated
journey remains the product acceptance authority.

### Local acceptance runner

A cross-platform Node runner owns orchestration. It generates a unique Compose
project name, loopback ports, Redis password, internal worker token, and local
Restaurant demo table token in memory. It never writes or prints their values.
It starts the existing Compose topology, waits for health, runs the dedicated
template acceptance spec, and always tears down run-owned resources on success,
failure, or interruption.

The runner refuses fixture mode for product acceptance. The template journey
does not require `OPENAI_API_KEY`. A separate guarded Describe command may use
the existing environment-only model key and must preserve Task 9's no-fallback
and no-raw-model-evidence controls.

### Product journey coverage

The full-stack template spec starts from the real Home template entry, not a
mocked route. It proves:

- curated template discovery and instantiation;
- editable customer and merchant preview state;
- at least one persisted Draft edit;
- immutable Publish and digest-bound Compilation;
- customer, merchant, shared-state, and cleanup verification evidence;
- a running generated customer surface and merchant surface;
- one customer order reflected in merchant kitchen/cashier state; and
- explicit preview stop plus empty run-owned resources.

Existing Workbench, Control Plane, compiler, Graph, and generated Restaurant
contracts are consumed unchanged. A failure that requires changing one of
those contracts stops the task and returns it to PM/Tech Lead scope review.

## Error handling

- Unsupported Node or pnpm fails before install or runtime work.
- Missing Docker or an inactive Docker server fails before Compose mutation.
- Missing `.env` or required names reports names only, never values.
- Port or project-name conflicts fail closed before the Playwright journey.
- Acceptance failure retains a bounded command/status summary and still runs
  teardown.
- Cleanup failure changes the final result to failure and lists only safe
  run-owned resource identifiers.
- Interruption handlers attempt teardown once and preserve the original exit
  reason when cleanup succeeds.

## Acceptance gates

The iteration candidate is accepted only when all of the following are fresh:

1. Doctor tests demonstrate expected RED/GREEN behavior for supported and
   unsupported Node, pnpm, Docker, environment-name, and secret-redaction cases.
2. The toolchain doctor passes on Node `22.11.0` with pnpm `9.0.0`.
3. The deterministic CI matrix passes on Node `22.11.0` and current `22.x`.
4. The dedicated local template journey passes from a clean database and
   isolated stack without a model credential.
5. Publish, Compile, verification, customer order, merchant fulfilment, and
   preview cleanup all pass in that journey.
6. Axe reports zero WCAG 2 A/AA violations at desktop and 390 by 844 pixels.
7. The run leaves exactly zero run-owned containers, networks, volumes, and
   preview directories.
8. Existing relevant Workbench, Control Plane, compiler-worker, compiler,
   capabilities, and product-recipe tests, typechecks, and builds pass.
9. No credentials, environment values, raw prompts, or raw responses appear in
   tracked changes or safe acceptance evidence.
10. Independent task review, QA, and final release review report P0/P1 = 0/0.

The historical Task 9 real-model pass remains relevant regression evidence.
One fresh guarded Describe run is required only for a new repository release,
not for every deterministic local acceptance run.

## Delivery

Implementation occurs on `codex/post-v0.1-local-readiness`. The controller is
the only normal commit and push owner. Each task follows focused TDD, an
independent task review, required QA, and fresh verification. Integration into
`main` follows `docs/delivery-policy.md`; this iteration does not create a
repository release or cloud deployment without separate authorization.
