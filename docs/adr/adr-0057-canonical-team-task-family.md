# ADR-0057: Canonical Team Task Family

## Status and recommendation

**Proposed** | Accepted | Rejected | Superseded | Deprecated

Recommendation: **experiment** with one canonical `team-task-tracking` definition and a structurally selected `task-v1` generated presentation. This is a bounded third runtime family, not an Expense rename or a claim of general project management. The reviewed local definition owns the complete blueprint; the model may select it or return material questions.

This proposal is not accepted and authorizes no production-file write, provider call, Product Publish, Compilation, Preview, Git action, external resource, deployment, or release. Implementation waits for acceptance and completion of the frozen ADR-0056 repair. PM must then record ownership before source changes.

## Context and reuse decision

- **CTX-001**: The delivered bank has exactly three canonical definitions (`restaurant-ordering`, `expense-approval`, `purchase-request-approval`) and two generated runtime families. Counts become four and three only after this experiment is implemented and evidenced.
- **CTX-002**: Current generic composition already derives persistent CRUD records, declared role permissions, workflow states/events, list/form/detail/queue pages, status filtering, refresh, and server-side role/state enforcement from an immutable Published Graph. It does not contain a reviewed Task definition or Task presentation selector.
- **GAP-001**: `factory.product-blueprint/v1` currently excludes the truthful Task events `start`, `complete`, and `reopen`. Aliasing them to approval verbs would corrupt labels, permissions, and acceptance evidence. Add exactly these three bounded verbs before registering Task.
- **REU-001**: Reuse in required order: `@factory/ui-primitives@0.1.0` native input/select/button/card/badge; `@factory/ui-patterns@0.1.0` form, loading, empty, error, confirmation, denial, and compact navigation patterns; ADR-0055 finder behavior; the accepted ADR-0056 private workspace recipe; existing Workbench structural-family logic; generated form/record/event runtime; and existing compiler fixtures. Restaurant assets have commerce bindings, approval definitions encode submit/approve/reject, and no pinned study supplies Task identity or access semantics. No copied source or new study is needed.
- **GAP-002**: After ADR-0056 acceptance, extract presentation-neutral private workspace helpers while preserving approval bytes, then add factory-authored `task-workspace-presentation@1.0.0`, license `UNLICENSED`, with the exact reuse manifest above. It remains compiler-private, unexported, and absent from public registries.

## Frozen canonical Task contract

- **TSK-001 — Supported business**: `team-task-tracking` is a local shared team board. A team member creates a task, starts it, completes it, and can reopen completed work; a viewer reads the board. Data persists through reload and status remains discoverable through the existing finder.
- **TSK-002 — Roles and permissions**: Exact actors are `member` / `Team member` and `viewer` / `Viewer`. Member has `create`, `read`, `start`, `complete`, and `reopen` on `task`; Viewer has only `read`. Both roles see all task records. The server remains authoritative for every role/state transition.
- **TSK-003 — Entity and fields**: The only business entity is `task` / `Task`, with fields in this order: `title` / `Title` / `text` / required; `description` / `Description` / `long-text` / optional; `assignee` / `Assignee` / `text` / required; `dueDate` / `Due date` / `date` / required; `priority` / `Priority` / `enum` / required, options exactly `low`, `medium`, `high`. Values render as escaped Graph data. Dates use existing safe date formatting; no locale, duration, currency, or urgency is inferred.
- **TSK-004 — Lifecycle**: Workflow `task-lifecycle` has ordered states `not-started`, `in-progress`, `completed`; `start` moves not-started -> in-progress by Member, `complete` moves in-progress -> completed by Member, and `reopen` moves completed -> in-progress by Member. Transition labels are `Start`, `Complete`, and `Reopen`. Initial status is `not-started`.
- **TSK-005 — Pages and journeys**: Exact Task-bound pages are `task-overview` / `Task overview` / dashboard, `task-list` / `All tasks` / list, `task-form` / `New task` / form, `task-detail` / `Task details` / detail, and `task-queue` / `Task workflow` / queue. Journeys prove create -> start -> complete and reopen -> complete; Viewer reads and is denied create and every event. `businessParameters` is always `null`.
- **TSK-006 — Assignment/access truth**: `assignee` is display text only. It is not a principal reference and does not restrict reads or actions. There is no user account, invitation, team membership, owner-only or assignee-only access, personal/private task, SSO, or tenant boundary. Any prompt requiring those semantics returns `needs-clarification`; the adapter must not imply identity from an assignee string.
- **TSK-007 — Material limits**: Edits after creation, custom/optional fields or states, delete/archive, subtasks, dependencies, recurring tasks, comments, attachments, reminders or external notifications, calendars, integrations, estimates, time tracking, bulk actions, and automation require explicit material clarification. Accepted omission means the exact scope above. No task audit or notification-delivery claim is made.

## Deterministic selection and generated presentation

- **DEF-001**: Add one private self-contained Task definition entry; do not generalize the fixed approval factory from a single non-approval example. It owns the strict selection schema/JSON branch, compact instruction, canonical requirement/blueprint, checksum, questions, and projector. The bank registration order appends Task after the three delivered definitions and validates family/parameter consistency.
- **DEF-002**: The provider Zod schema, JSON Schema enum, and instruction vocabulary add the same three verbs. Unknown keys, provider-supplied structure for a supported Task, non-null parameters, unresolved material differences, and mixed selection/generated-blueprint results fail closed under existing rules.
- **FAM-001**: Workbench classifies `task` only when exactly one Blueprint entity has the five TSK-003 fields with exact semantic keys, types, requiredness, and `priority` option set; exactly one workflow on it has initial `not-started`, the exact three-state set and TSK-004 transition triples; exactly two actors have, on that entity, respectively the exact sets `create/read/start/complete/reopen` and `read`, with no other entity, grant, event authority, or actor; and exactly one each of dashboard/list/form/detail/queue is bound to it, with no other page intent. Application, definition, entity, workflow, page, actor, and title/label identifiers may differ; semantic field/state/event keys may not. Fields, options, actors, grants, pages, transitions, locks, and bindings are set-matched independent of declaration order; the first workflow state must still be `not-started`, and the canonical definition still emits TSK-002/003 order.
- **FAM-001A**: Require checksum parity and exactly the six unique locks `core.crud@1.0.1`, `core.workflow@1.0.1`, `core.identity-policy@1.0.0`, `core.policy-declarations@1.0.0`, `core.audit@1.0.2`, `core.notification@1.1.1`. Require exactly nine unique bindings and no others: CRUD `entityKey` -> the Task entity and `routeKey` -> its sole list page; Workflow `flowKey` -> its sole workflow; Identity `principalEntity` and `sessionEntity` -> the base application principal/session symbols, `defaultRole` -> first declared actor and `authenticatedRole` -> second; Audit `actorRole` and Notification `recipientRole` -> first declared actor. Reordering actors changes those four planner-derived role bindings but not Task eligibility. The notification lock creates no Task effect or delivery claim.
- **FAM-002**: The Workbench delivery surface handles `task` explicitly: label and accessible name are `Task`, heading is `Your Task app`, progress uses Task rather than Restaurant fallback, and scope copy states local shared board, selectable demo roles, role-wide Member actions, Viewer reads, and display-only assignee. Existing Restaurant and Approval strings/behavior remain exact.
- **UI-001**: Compiler profile `task-v1` requires exactly one qualifying Graph flow/entity projection of FAM-001: entity fields are `title` string required, `description` text optional, `assignee` string required, `dueDate` date required, `priority` required enum with exactly low/medium/high, plus injected required `status` enum with exactly the three states; flow initial/state/event/transition/role relations exactly implement TSK-004; business permissions on that entity exactly implement TSK-002; and pages contain exactly one bound block of each derived type `stats`, `list`, `form`, `detail`, and `queue`, with no other block/page for it. Generated principal/session entities and their standard permissions are allowed but never qualify the profile. IDs, labels, and declaration order are ignored; semantic keys are not. Zero or multiple qualifying flows, or any missing/extra field, state, event, transition, business grant, page, or block selects legacy and never a partial Task treatment. A match composes the repaired workspace, native mobile disclosure, neutral compact rows, typed form, finder/count/no-data/no-match behavior, race guards, retained results, denials, refresh, and persistence using exact Graph labels/values and humanized semantic keys, with no approval copy.
- **UI-002**: Promote only unique exact `title` string as row heading and show declared `priority`, `dueDate`, `assignee`, and status summaries. Other fields and ID remain in Details. Reuse only icons `house`, `receipt-text`, `user-round`, `refresh-cw`, `clock`, `circle-check`, `circle-x`; map start/active to clock, complete/completed to circle-check, and reopen to refresh-cw. Status alone receives accent. Legacy, Restaurant, and approval output bytes remain exact.

## Compatibility, security, catalog, and operability

- **API-001**: The Blueprint V1 grammar change is additive for producers and current Graph composition because Graph actions/events are generic identifiers. Old Blueprint, Graph, API, and stored record data remain valid. Strict downstream consumers must update their three enumerations atomically; no API endpoint or serialized Graph version changes.
- **SEC-001**: Existing local demo role selection is not authentication. Browser visibility grants no authority; server role/state checks and safe errors remain decisive. No credential, tenant, file, external data, provider, or network boundary changes. Synthetic evidence must never retain raw prompts/responses or secrets.
- **CAT-001**: Public capability/UI/recipe catalogs and their counts remain unchanged. The bank gains one private reviewed definition and the compiler gains one private recipe descriptor with factory provenance. No package, notice, dependency, source intake, dynamic plugin, or runtime registration is added.
- **OPS-001**: Existing CRUD/event persistence, health, immutable Compilation, Preview, and teardown procedures apply. Large-list pagination, real identity, hosted deployment, external notifications, and multi-tenant operations remain unsupported.

## Consequences and alternatives

- **POS-001**: One ordinary-user prompt can produce a coherent task board with a complete create-to-reopen journey, while a reusable structural family prepares later reviewed Task definitions.
- **NEG-001**: Same-version additive Blueprint vocabulary requires synchronized strict-consumer changes; the first Task definition intentionally supports only a shared local board.
- **ALT-001 — Reuse approval verbs or rename Expense**: Rejected because submit/approve/reject misstate Task behavior and permissions.
- **ALT-002 — Let the model generate arbitrary Task blueprints**: Rejected because it restores structural reproduction effort and can silently invent identity, assignment, and workflow semantics.
- **ALT-003 — Build full identity and project management now**: Rejected for this experiment because owner/assignee enforcement, tenancy, collaboration, and integrations require separate Graph/security decisions.
- **ALT-004 — Add a UI framework or public recipe**: Rejected because native controls and the accepted private workspace meet the contract; another dependency or public boundary adds no required capability.
