# ADR-0060: Approval Correction, Resubmission, and Mutation Recovery

## Status and recommendation

**Proposed** | Accepted | Rejected | Superseded | Deprecated

Recommendation: **migrate** future canonical Expense and Purchase Request interpretations from the private one-stage approval definition contract to `approval-definition-template@2.0.0`. Compile only its exact correction shape with private generated contracts `factory.generated.approval-correction/v1`, `factory.generated.approval-mutation/v1`, and `factory.generated.approval-decision-event/v1`. Keep old Published Graphs and Compilations on their existing behavior and exact bytes. This proposal is not accepted and authorizes no source change, Product Publish, Compilation, provider call, external resource, deployment, Git action, or release; independent standing acceptance and a PM ledger record are required first.

## Context and verified gap

- **CTX-001**: Current canonical approval definitions grant requester create/read/submit, use `draft -> submitted -> approved|rejected`, and explicitly exclude return/reopen/resubmit. Generated storage has a generic update primitive, but the approval API and UI expose no governed edit. Current decision evidence has no reason field.
- **CTX-002**: A correction loop adds several state-changing requests. `docs/threat-model.md` requires every such request to bind idempotency and optimistic concurrency or immutable revision. Deferring this contract would let a lost Return or PATCH response be retried in a changed state, duplicate evidence, or overwrite a concurrent edit.
- **CTX-003**: `factory.product-blueprint/v1` already admits `update`; `factory.application-graph/v1` admits the required states, events, roles, grants, and loop. Its action uniqueness rule makes `update: returned -> draft` the smallest valid second transition rather than another `submit`. No Graph V2 or action verb is needed.
- **REU-001**: Reuse `core.crud@1.0.1`, `core.workflow@1.0.1`, `core.audit@1.0.2`, identity/policy checks, `RecordStore.update/inTransaction`, declared field controls, record finder, phase/scope guards, Details, ADR-0058 presentation, and ADR-0059 history. The first-party private Restaurant command implementation supplies the proven transaction pattern: scoped key, canonical payload hash, persisted outcome, unique constraint, conditional version write, replay, and rollback tests. Its domain contract cannot be reused directly. Add one distinct compiler-private approval mutation emitter/descriptor; no dependency, public registry item, copied source, or capability version is justified.

## Frozen definition and eligibility

- **DEF-001 — Canonical loop**: Keep existing definition keys, business fields, selection envelope, pages, actors, exclusions, and counts. Expense and Purchase requester grants become exactly `create, read, update, submit`; reviewer stays `read, approve, reject`; auditor stays `read, audit`. States are exactly `draft, submitted, approved, returned`. Transitions are `submit: draft -> submitted` by requester, `approve: submitted -> approved` by reviewer, `reject: submitted -> returned` by reviewer, and `update: returned -> draft` by requester, labelled Submit, Approve, Return, and Revise. Repeated return/revise/resubmit is supported; approved is terminal.
- **DEF-002 — Truthful limits**: Update instructions, guides, journeys, checksums, and clarification rules for only this loop. Multiple/sequential approvers, requester ownership/private records, verified identity/SSO/tenant isolation, submitted or approved edits, configurable reason policy, attachments, thresholds, currency semantics, external integrations, and notifications beyond accepted local effects remain material questions. Selection never lets a model supply workflow, permissions, mutation fields, routes, code, or versions.
- **SEL-001 — Fail-closed selector**: Select `approval-correction@1.0.0` only for one unambiguous structural approval flow with the exact states/transitions/grants above, one bound form plus readable list/queue/detail coverage, and exact locks `core.crud@1.0.1`, `core.workflow@1.0.1`, `core.identity-policy@1.0.0`, `core.policy-declarations@1.0.0`, `core.audit@1.0.2`, and `core.notification@1.1.1` with canonical bindings. Actor/entity/page IDs and order may differ; semantics may not. Missing/extra/duplicate states, events, grants, flows, pages, bindings, locks, or checksum fail closed or use existing behavior; correction is never partially emitted.

## Frozen generated API, idempotency, and concurrency contracts

- **API-000 — Exact entity boundary**: API-001..006, Factory-owned versioning, receipts, reason persistence, correction transitions, and the new PATCH route apply only to the unique entity bound to the exact approval flow selected by SEL-001, called `approvalEntity`. The secondary requester/profile entity keeps its current list/read and policy-denied create/transition behavior, its existing internal update grant is not exposed as an HTTP mutation, it receives no version/receipt fields, and PATCH returns the same safe 404/no-write behavior as before. No other entity gains a generic mutation route.
- **API-001 — Common command identity**: Every `approvalEntity` POST/PATCH mutation requires `x-factory-idempotency-key` matching `[A-Za-z0-9._:-]{1,128}`. The server authorizes the resolved role/session first. It derives `actorScope` from the validated fixture-session ID in fixture mode and otherwise from the current local profile's resolved role string; this remains a local role identity, not a verified person. `scope` is SHA-256 of the length-delimited tuple `(Published Graph checksum, actorScope, role, entity, record ID or $create, operation/event)`. `requestHash` is SHA-256 of validated JSON canonicalized recursively with lexicographically sorted object keys. Raw keys, payloads, and reasons are never logged. A missing/malformed key or body is safe 400.
- **API-002 — Receipt and replay**: Correction output adds immutable-after-commit `ApprovalMutationReceipt { id String @id @default(cuid()), scope String, idempotencyKey String, requestHash String, operation String, recordId String, responseStatus Int, responseBody Json, createdAt DateTime @default(now()), @@unique([scope, idempotencyKey]) }`. Authorization precedes receipt lookup. First execution writes the receipt, record/status/version, decision audit event, declared capability effects, and accepted local outbox work in one transaction. Create stores status 201; other mutations store 200; every success body is the exact serialized `StoredRecord` with `id`, `status`, `version`, and declared values. A same-scope/key/hash retry returns that stored status/body and identical record ID/version without another record, version increment, event, effect, or outbox entry. Same key with a different normalized request returns safe 409 `approval.idempotency_conflict`. A failed or denied transaction leaves no receipt.
- **API-003 — Create**: `POST /api/:entity` body is exactly `{ values: Record<string, unknown> }`. Values obey declared field types and exclude Factory-owned `id`, `status`, `version`, timestamps, and relations. Because no record exists to version-check, the command binds to the immutable Published Graph checksum and creates exactly one `draft` record at Factory-owned integer `version: 0`, one `create` audit event with null reason, and one receipt atomically. A retry after a lost response replays the same record rather than creating another.
- **API-004 — Update**: Add `PATCH /api/:entity/:recordId` only to correction output. Body is exactly `{ expectedVersion: nonnegative safe integer, values: Record<string, unknown> }` with at least one own value key. Unknown, inherited, accessor, malformed, empty-required, invalid typed, or Factory-owned keys are safe 400. Require exact Graph `update`. A conditional write matches ID, expected status, and `version = expectedVersion`; draft changes supplied fields only, while returned changes fields and applies `update -> draft`. Success preserves ID, increments version exactly once, and writes one null-reason `update` event. Submitted/approved or direct `POST .../events/update` is safe 403 with no write.
- **API-005 — Submit, approve, and return**: Transition POST bodies are exactly `{ expectedVersion }` for submit/approve and `{ expectedVersion, reason }` for reject/Return. Reason is trimmed, 1..500 UTF-16 code units, excludes NUL, DEL, and C0 controls except tab/newline/carriage return, persists exactly as untrusted plain text, and renders escaped. Each transition conditionally matches ID, from-state, and version; success increments version once. Approve/submit events have null reason; reject writes `{ actor, action: "reject", entity, recordId, reason, at }`. Status, event, effects/outbox, and receipt commit or roll back together.
- **API-006 — Conflict semantics and precedence**: For an `approvalEntity` record command, evaluation order is exact: current authorization -> scoped receipt lookup/hash comparison and replay -> record existence -> expected-version comparison -> same-version state/transition validation -> conditional mutation. Version mismatch always returns safe 409 `{ code: "approval.version_conflict", current: { id, status, version } }`, even when the current state would also reject the command; a same-version wrong state is safe 403. A concurrent conditional-write loser after validation also returns that authoritative 409. These errors expose no business values and write no receipt/evidence. Two simultaneous identical key/hash commands yield one commit plus one replay; identical key with differing hash yields one commit plus one idempotency conflict.
- **API-007 — Readable decisions**: Add authenticated `GET /api/:entity/:recordId/decision-events` only for `approvalEntity`; other entities retain safe 404. Enforce read on the approval entity and record existence, then return only persisted approve/reject events in ascending storage order as exact `factory.generated.approval-decision-event/v1` objects `{ actor, action, entity, recordId, reason: string|null, at }`. Existing `/api/audit` remains audit-authorized and adds nullable reason only for correction output. Old output keeps its exact five-field event response.
- **DAT-001 — Isolated storage**: Correction initial Prisma/SQL adds Factory-owned `version Int @default(0)` only to the `approvalEntity` record model, `reason String?` on AuditEvent, and the exact receipt model in API-002; the in-memory store has behaviorally identical coordination for tests. Receipt/result and decision rows are append-only after commit. Every Compilation still starts from an immutable Published Graph and its own initial schema; no historic database, row, Graph hash, lock, or artifact is migrated or rewritten.

## Generated interaction contract

- **UI-001 — Safe command lifecycle**: Create, Save, Submit, Approve, and Return generate one key per user activation and retain it across an unknown-result retry; editing a retained payload creates a new key. The UI sends the displayed record version, disables all mutations for that record while pending, ignores repeat activation, and refreshes authoritative records after first success or replay. A 409 refreshes and shows a plain conflict message; it never automatically overwrites or retries with a new version.
- **UI-002 — Correction and reason**: Requesters see Edit only for draft/returned rows. The compact prefilled declared-field form preserves identity; returned Save becomes Draft, then the existing Submit action resubmits. Reviewers choosing Return receive one required labelled `Reason for return` textarea and cancel/Return actions. Submitted/approved expose no Edit. Failed Save/Return retains values and the same retry key.
- **UI-003 — History and scope**: Returned rows load their record-scoped decision events and show the latest persisted return reason before Edit. ADR-0059 loading/empty/error/retry and role/entity guards apply; late privileged responses cannot repopulate another scope. Earlier reasons remain after resubmit and later approval. Render no raw JSON, invented person identity, currency, locale, or ownership claim.

## Compatibility, security, catalog, and operability

- **SEC-001**: Browser visibility grants nothing. Server policy, exact state, conditional version, field validation, and transition shape remain authoritative. Current local-demo reads are role-wide, and audit actor remains the resolved role rather than a verified person; this proposal does not claim owner privacy, tenant isolation, or real identity. Safe errors never echo payloads, reasons, contents, policy internals, or stacks. Replayed results require current authorization.
- **CAT-001**: Private definition behavior advances to `2.0.0`; delivered definition/family counts remain three/two until an accepted implementation ships. Capability, product-recipe, UI, screen-recipe, compiler-target, and source-study catalog counts/locks remain unchanged. The private descriptor is factory-authored, `UNLICENSED`, and unexported. No package, lockfile, license, icon, font, provider, credential, network, Docker, Compose, port, queue, service, or external resource changes.
- **OPS-001**: Generated correction deployments add bounded receipt/audit storage and routes, with no service or topology change. A process crash before commit leaves nothing and retry executes once; a crash after commit replays the persisted outcome after restart. Receipt retention follows the generated application's existing data retention because premature deletion breaks replay. This slice closes local uncertain-write and concurrent-write safety for Create/PATCH/submit/approve/return. Future recovery work is limited to separately governed external-provider delivery reconciliation, verified identity/tenant boundaries, and operational backup/restore; none is claimed here.

## Consequences and alternatives

- **POS-001**: An ordinary requester can create once, correct before submission, understand a return, revise the same record, resubmit, and retain both decisions after reload; retries and concurrent edits cannot silently duplicate or overwrite the journey.
- **NEG-001**: The private generated API/data surface grows, every mutation needs a client key/version discipline, and role-wide demo reads expose reasons for records already readable to that role. Receipt retention consumes bounded storage proportional to successful commands.
- **ALT-001 — Store latest reason on the record**: Rejected because it overwrites history and cannot bind the explanation to a decision.
- **ALT-002 — Grant requesters audit**: Rejected because UI convenience cannot widen authority; record-scoped decision reads are narrower.
- **ALT-003 — Graph V2 or new verbs**: Rejected because V1 `update/reject/submit` expresses the bounded loop; a public migration is disproportionate.
- **ALT-004 — Return directly to draft or combine revise and submit**: Rejected because it hides returned state or creates a larger compound business command. Returned -> Revise -> Draft -> Submit is explicit, with every mutation independently atomic and retryable.
- **ALT-005 — Defer idempotency/concurrency**: Rejected because it violates the threat-model mutation invariant and makes the correction loop unsafe under lost responses or concurrent writes.
- **ALT-006 — Keep terminal rejection**: Rejected because it forces duplicate requests and fails the authorized product outcome.
